# Brechas del backend y feature flags

El frontend no inventa endpoints. Cada función que el backend aún no soporta se programa
contra un **puerto** con dos adaptadores: uno HTTP (contra el contrato propuesto) y uno
simulado o local. El flag de `environment.features` decide cuál se inyecta
(`src/app/core/config/ports.providers.ts`). Para pasar a lo real basta con poner el flag en
`true`: ninguna pantalla cambia.

En desarrollo, la insignia **Modo demo** (abajo, al final de cada página) lista los flags
apagados y permite descargar el log del frontend como `.txt`.

## Otros puntos del backend que afectan al frontend

- **Seguridad:** el backend emite JWT pero no tiene middleware de autenticación ni de roles. El frontend envía siempre `Authorization: Bearer <token>`, protege rutas por rol y trata 401/403 como cierre de sesión. Mientras tanto, `GET /api/envios/:id` es público e incluye el PIN; el frontend lo descarta en las vistas del conductor y no muestra envíos de otro cliente, pero la protección real debe estar en el backend.
- **Envío desde Asignado:** el backend permite validar la entrega sin pasar por En Ruta (el CU-009 exige En Ruta).
- **Un servicio activo por conductor (RN_OP_002):** el backend no lo valida. El frontend lo recuerda localmente (`ActiveServiceStore`) y bloquea aceptar otro.
- **Aprobación:** `POST /api/envios/aceptar` no verifica que el conductor esté aprobado; el frontend sí bloquea el tablero.
- **Errores de archivo:** según el código actual, un error de `multer` (tamaño o tipo) en `/api/documentos/upload` pasa al manejador global y llega como 500 genérico, no como 400. El frontend valida tipo y tamaño antes de subir y traduce "File too large" si llegara.
- **Administrador sembrado:** el hash de `seed.sql` no corresponde a ninguna contraseña conocida.
